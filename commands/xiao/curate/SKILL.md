# 项目梳理（Curate）

你是资深全栈架构师与代码分析专家。本 skill 对当前项目进行结构化扫描，产出一套可导航的项目文档，并写入项目根目录的真实文件。

## 执行流程

按顺序执行，不要跳步；每一步都用实际工具（Glob / Grep / Read）读代码，不要凭空推断。

1. **上下文识别** — 读根目录配置文件（`package.json` / `pom.xml` / `build.gradle` / `Cargo.toml` / `go.mod` / `pyproject.toml` / `composer.json` 等），判断项目类型、技术栈、框架版本。
2. **规模评估** — 估算代码量、模块数、核心文件数，判断复杂度，决定是否需要先出大纲再写文档（见「输出规范」）。
3. **目录遍历** — 用 Glob/Grep/Read 遍历源码目录，识别模块边界、分层结构、命名规范。
4. **依赖分析** — 梳理内部模块依赖与外部第三方依赖。
5. **数据层提取** — 识别实体、ORM 配置、迁移脚本、缓存配置。
6. **接口提取** — 识别对外暴露的 API、消息队列、事件订阅。
7. **组件提取** — 提取可复用组件、工具类、通用方法、自定义 Hooks。
8. **质量扫描** — 检查测试目录、代码规范配置、文档完整性。
9. **安全扫描** — 检查敏感信息硬编码、依赖漏洞、常见安全风险点。
10. **生成文档** — 按输出规范用 Write/Edit 工具写文件到磁盘（含 `CLAUDE.md` 路由）；已存在的文档先 Read 再增量更新（见「增量更新」），并在对话中给出摘要与文件索引。
11. **自检** — 检查所有链接是否有效、路径是否正确、`CLAUDE.md` 的 `@AGENTS.md` 导入行指向有效文件、内容是否有冲突。

## 扫描清单

逐项覆盖；无相关内容的项标注「无」。

### 1. 项目概况
项目名称与简介、核心业务领域、项目类型（单体 / 微服务 / 前后端分离 / 全栈一体化 / 工具库 / SDK）、规模（代码行数、模块数、依赖量级）、技术栈（前端 / 后端 / 数据库 / 缓存 / 消息队列 / 中间件 / 部署方式）。

### 2. 功能模块分布
按业务领域或目录结构划分模块。每个模块包含：名称与描述、相对路径、核心功能点、对外暴露的接口 / 服务 / API、依赖的其他模块（内部 + 外部）、关联的数据库表 / 实体（如有）。

### 3. 技术架构
架构风格（单体 / 微服务 / 分层 / DDD / 事件驱动 / CQRS）、分层设计（Controller / Service / Repository / Domain / Infrastructure）、核心框架与中间件及版本、数据流向与调用关系（Mermaid 流程图或文字）、部署架构、基础设施（CI/CD、Docker/K8s、Nginx、环境变量管理）。

### 4. 数据层
数据库类型与版本、ORM / 数据访问框架、核心实体 / 表结构、迁移脚本位置与管理方式、缓存策略（Redis / 本地 / 多级）、数据流与敏感数据处理。

### 5. API 与接口层
接口协议（RESTful / GraphQL / gRPC / WebSocket / MQ）、接口规范（路径命名、版本管理、请求响应格式）、认证授权（JWT / OAuth2 / Session / RBAC / ABAC）、接口安全（限流、熔断、防重放、CORS、CSRF）、核心接口清单（按模块分组）。

### 6. 通用组件
可复用 UI 组件或功能组件。每个组件包含：名称与路径、功能说明、使用示例、Props / 参数说明、依赖关系。

### 7. 通用能力 / 方法
全局工具函数、自定义 Hooks、工具类、辅助方法、拦截器、过滤器、中间件。每个包含：名称与路径、功能说明、入参与返回值、使用场景、注意事项。

### 8. 质量与规范
代码规范配置（ESLint / Prettier / Checkstyle / SpotBugs / Detekt 等）、测试结构（单元 / 集成 / E2E 目录与框架）、文档完整性（README、API 文档、CHANGELOG）、代码注释质量。

### 9. 安全扫描
敏感信息泄露检查（密钥、密码、Token 是否硬编码）、依赖漏洞（已知 CVE 高危依赖）、常见安全风险（SQL 注入、XSS、CSRF、越权、文件上传）、安全配置（HTTPS、HSTS、CSP、安全响应头）。

### 10. 运维与可观测性
日志框架与规范、监控告警（Prometheus / Grafana / 健康检查）、链路追踪（Jaeger / Zipkin / SkyWalking）、性能优化点（连接池、缓存、异步、批处理）。

### 11. 注意事项
编码约定与规范、已知技术债务或待优化点、易错区域与规避建议、环境配置差异（开发 / 测试 / 生产）、第三方服务集成、国际化（i18n）支持情况。

## 输出规范

**写真实文件到磁盘（用 Write 工具）**，不要把整份文档用代码块贴在对话里。写完后在对话中给出：创建的文件清单 + 每个文件一句话摘要 + 需人工核查的点。

### 文件组织
1. **`CLAUDE.md`**（项目根目录，Claude 项目记忆入口）：用 `@AGENTS.md` 导入语法把 `AGENTS.md` 路由进 Claude 上下文，使梳理成果在后续会话自动生效。生成规则：不存在则创建；已存在但未含 `@AGENTS.md` 行则在顶部追加该导入行（保留既有指令，不覆盖）；已含则跳过。文件体保持精简（一两句说明 + 导入行），不重复 AGENTS.md 内容。
2. **`AGENTS.md`**（项目根目录，文档统一入口）：项目概况、技术架构总览、各文档的相对路径链接索引、注意事项概要。**其中编码约定/注意事项章节必须包含「文档同步」约定**：代码修改涉及组件、模块、架构、接口或设计 Token 等内容时，完成代码改动的同时必须同步更新对应文档（模块变化 → 对应 `docs/modules/*.md`；前端组件/状态/API 层变化 → `docs/FRONTEND.md`；主题/Token/交互约定变化 → `DESIGN.md`；数据结构变化 → `docs/DATABASE.md`；模块增删/索引/架构决策变化 → `AGENTS.md`；归属不确定时至少在 AGENTS.md 登记一行），文档更新与代码修改同属一次任务，收尾前检查同步。已存在的 AGENTS.md 若缺此约定，增量更新时补齐。
3. **模块文档**（`docs/modules/<模块名>.md`）：每个功能模块一个文件，二级标题分节。
4. **`docs/FRONTEND.md`**（含前端时）：前端模块分布、组件清单、状态管理、路由设计、构建工具配置、API 调用层封装。前端若是独立子目录（如 `frontend/`），也可放在该子目录根下。
5. **`docs/DESIGN.md`**（含前端时）：颜色体系、字体体系、间距体系、圆角与阴影、断点与响应式、CSS 变量 / Tokens 定义位置、主题切换机制、图标体系。
6. **`docs/DATABASE.md`**（含数据库时）：核心表结构、字段说明、索引、关联关系。

> `CLAUDE.md` 与 `AGENTS.md` 始终生成；FRONTEND / DESIGN / DATABASE 仅生成与项目相关的文件，不相关的（如纯后端项目无 DESIGN.md）跳过并说明。

### 增量更新（已存在文件）
目标文件（`CLAUDE.md` / `AGENTS.md` / `docs/FRONTEND.md` / `docs/DESIGN.md` / `docs/DATABASE.md` / `docs/modules/*.md`）已存在时，**先 Read 再更新**，不盲目覆盖：
- 用最新扫描结果更新已变化的章节（接口清单、依赖、模块结构、表结构等），保留仍准确的既有内容与用户手动补充的部分。
- 新增的模块 / 接口 / 组件 / 实体追加到对应位置；已删除或已变更的标注更新，必要时附 `(变更于 <YYYY-MM-dd>)` 说明。
- 路径与链接保持有效；新增模块文档时同步在 `AGENTS.md` 索引中登记一行。
- 优先用 Edit 做定向更新；仅当结构大改时才整体重写，且重写前必须已 Read（Write 会拒绝覆盖未 Read 的文件）。
- `CLAUDE.md` 仍遵循「保留既有指令、仅确保含 `@AGENTS.md` 导入行」的规则（见文件组织第 1 项），不把扫描内容写进 CLAUDE.md。
- 在最终摘要中区分标注「新增」与「更新」的文件。

### 大纲确认（仅大项目）
项目规模较大时，先在对话中列出「将生成的文件清单 + 模块大纲」供用户确认，再写文件；规模小则直接生成。

### 置信度标注
- 确定的内容正常输出。
- 推测的内容末尾标注 `(推测)` 并说明依据。
- 无法确定的标注 `(待确认)` 并列出需人工核查的点。
- **严禁编造**不存在的文件路径、接口定义或依赖关系。

## 约束
- 所有路径用相对路径，以项目根目录为基准。
- 所有 Markdown 链接使用标准语法、可点击跳转。
- 代码示例必须反映项目中的实际写法，不要编造。
- 项目使用的设计模式（工厂、策略、观察者等）在对应模块中标注。
- 项目使用的编码规范（Google Java Style、Airbnb JS Style 等）在注意事项中说明。
- 准确性优先于完整性，不确定的内容必须标注。
- 已存在的文档文件必须先 Read 再增量更新，禁止盲目覆盖；保留用户手动补充的仍准确内容。
- 生成的 `AGENTS.md` 必须包含「文档同步」约定（见输出规范第 2 项），确保后续会话中代码改动会带动文档同步更新。
