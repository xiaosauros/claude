# 终端/TUI 内中文 IME 吞字与误删问题

> 适用场景：xterm.js 等终端模拟器、CLI TUI（Claude Code / Cursor CLI 等 Ink 系）内接中文输入法，WebView2 / WKWebView 嵌入环境。与 `ime-enter-send-issue.md`（输入框 Enter 发送）互补：那份管普通输入框，这份管终端内嵌的 IME 代理框与子进程链路。

## 一、左上角吞字（候选窗甩到左上角 / 连词只上屏首字）

不是单一根因，是同一条链上多个独立成因，必须逐个排查而不是反复收窄时间窗：

- **退化模式（零 composition）**：WebView2 下微软拼音可能整条会话零 composition 事件，确认候选词被拆成多个逐字 `insertText`（间隔可 <5ms）。若每个 insertText 各包一次 bracketed paste 发给子进程，TUI 会把 5ms 内连续到达的第二个 paste 整个丢掉 → 「连词只上屏首字」。修法：IME 文本出口微合并——剥壳拼接后在数毫秒窗口（t0 取 6ms）统一包一次 paste，与正常 composition 的整词提交形态一致。
- **预编辑浮层跟着硬件光标走**：xterm 自己的 `.composition-view` 只按硬件光标格摆放，而 CLI TUI 常把硬件光标钉在 (0,0)（发 `?25l` 藏光标），浮层因此画在终端左上角；且它挂在 `position:absolute; top:0` 没有宽度的容器里，`max-width:100%` 解析成 0，用户从来看不见自己在打什么。修法：浮层钉到与 IME 代理框（textarea）同一处（`position:fixed`），宽度 `max-content`、上限按视口 clamp；只在 229→compositionend 之间且浮层激活时才读矩形，否则每帧白加一次强制重排。
- **组词期间锚点必须冻结**：Windows 上组词期每颗拼音字母的 keydown 也是 `keyCode===229`，若「见 229 就重读硬件光标重钉锚点」，TUI 每帧重绘把光标甩回 (0,0)，代理框在「底部组词区」与「左上角」之间跳，TSF 缓存的 caret 矩形被中途换掉后，IME 立刻退化成候选窗回原点 + 只提交首字，重复/吞字都是它的连锁。判据是「进入本次 keydown 前是否已在组词窗口内」（`composing || imePending`）而非 `composing`——输入法已收拼音而 Chromium 尚未发 `compositionstart` 的那一段（部分输入法/外挂）同样不能挪锚点。
- **代理框 value 累积**：兜底状态若释放不掉（见下条保质期），代理框 value 会跨多次提交累积成「你你你你」，正是候选窗回左上角的进料口之一；组词期间不得改 `textarea.value`。

## 二、删除误删（组词中按退格，TUI 里已有字符被同步删掉）

- **现象根因**：退化 IME（零 composition）下组词中每颗退格的 keydown 也是 229，被 229 还原表编成 `\x7f` 发给 TUI，同时 IME 在 OS 层删拼音——两条通道各删各的，表现为「删拼音把终端里已有字符删了」。
- **代价不对称，逐键问方向**：「无证据时放行还是 hold」的裁决不能全体键复用。Esc 猜错 = 多发一个字节，TUI 自己会处理（吞掉才误事）；退格猜错 = 多发一个 `\x7f` 真删一个字符（吞掉有保质期兜底、多发即破坏数据）。所以退格要单列：组词窗口内只删拼音不发字节，过期放行删终端字符，硬上限照旧兜底防永久吞键。
- **「输入法在收拼音」是猜测，必须有保质期**：从「229+字母」推出的猜测没有任何事件能证实或证伪；续期条件若写成「又有一颗候选键被 hold」就是猜测自我证明、永不过期（实测按住退格 3.6 秒零字节到 TUI）。两把尺子：滑动窗口（约 1200ms，从上一颗被 hold 的键起算，保连续选词）+ 硬上限（约 3000ms，从上一次正面证据——229 字母 / composition 事件——起算）。文本一旦经 insertText 上屏，立刻结束猜测，不等窗口。
- **吞键需正面证据**：取消/选词键（Esc、方向键、翻页、选词数字）的 hold 必须同时有「组词活着」的正面证据（composition 活着或预编辑数据未清）；不可证伪的猜测单独不配扣下高频键。Enter/Space 例外——提交不可逆，猜错方向不对称，维持 hold。

## 三、共通注意点

- **整词重复/吞字还有另一个引擎**：xterm `CompositionHelper` 对每颗 229 keydown 抓 `textarea.value` 做「整值 diff」当终端输入送出——变长且旧值非子串就整词重发、变短就发 DEL、等长不同就整值重送。修法是 `attachCustomKeyEventHandler` 对 229 keydown 返回 `false` 挡在 xterm `_keyDown` 之外；不要用 `stopPropagation`（会连 textarea 上其它监听一起掐掉），更不要用「文本匹配压重复」（挡不住无 input 事件的静默回写，却会把无 compositionstart 的合法提交整个吞掉）。
- **两层各自维护「IME 还在不在」时，谁说了算要收敛到一处**：锚点守卫层与输入兜底层若给出相反结论（守卫已放锚点、兜底还在吞键），代理框会被 TUI 重绘带着跳走且再钉不回来。发布「新鲜度函数」而非布尔快照（新鲜度是时间的函数，须在真要放的那一刻现算），接线走显式参数、不靠监听注册先后。
- **对第三方私有 API / 行为的结论以实抓为准**：依赖库私有字段会改名（如 xterm `_core._coreService` → `_core.coreService`，只读旧名回退永远 false）；TUI 实际发什么转义序列（藏不藏光标、发不发 DEC 2026/鼠标捕获）要拿真实字节抓包验证，不按旧记录推。
- **测试台接线必须与生产逐字一致**：装配顺序、监听挂接点不同的测试台，会系统性地让某类问题「门禁里永远绿、用户机器上反复红」；CDP/合成事件测不到真实 TSF 行为（退化模式整条会话零 composition 事件就是真机取证才拿到的），复现「测试台绿、用户机器红」时先取真机事件流时间线再动手。
